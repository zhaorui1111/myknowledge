# 结构化输出与确定性通信（Structured Outputs）

> 大语言模型（LLM）天生是一个基于概率分布的自回归文本生成器。然而，在以 AI Agent 为核心的现代软件系统中，下游代码（如数据库驱动、API 调用、业务状态机）需要的是 100% 具备确定性、符合严格模式（Schema）的强类型数据。若无法在非确定性的模型生成与确定性的程序逻辑之间建立钢铁契约，Agent 系统就会沦为不可控的玩具。本文将深入剖析大模型结构化输出的底层数学原理（约束解码与文法掩码）、主流云端 API 与本地推理引擎的双轨实战、复杂多态提取及自愈容错机制。

## 1. 为什么结构化输出是 AI Agent 系统工程的生命线

在传统的软件工程中，组件之间的交互协议是绝对确定性的：函数签名定义了严格的入参和返回值，RPC/REST 接口遵循契约式 Protocol Buffers 或 OpenAPI 规范。

然而，AI Agent 引入了一个前所未有的异构节点——**大语言模型**。大模型的输出本质上是自然语言序列。为了让 Agent 能够：
1. **可靠地调用外部工具（Tool Calling）**：向 SQL 引擎传递合法参数、向天气 API 传入精确经纬度；
2. **驱动复杂业务状态机（State Transitions）**：根据分类结果精准跳转到对应的分支节点；
3. **沉淀企业级业务对象**：将非结构化的法律文书、医疗病历或工程报价单精确解析为结构化数据库记录；

工程师就必须将大模型的“自由发散文本”锁死在严格的数据协议中。**结构化输出（Structured Outputs）不是可有可无的装饰品，而是 AI 融入现代确定性软件工业的唯一通信桥梁**。

## 2. 大模型随机性采样与 JSON 崩溃的底层根源

要解决问题，首先必须从自回归生成的数学机理理解为什么让 LLM 输出 JSON 如此容易崩溃。

### 2.1 自回归生成机制

现代 Transformer 语言模型在生成文本时遵循自回归假设（Auto-regressive）：

$$P(w_1, w_2, \dots, w_T) = \prod_{t=1}^T P(w_t \mid w_1, \dots, w_{t-1})$$

在每个时间步 $t$，模型基于前序已生成的所有 Token 计算当前隐藏状态，通过最终的线性头（Linear Projection）映射到整个词表（Vocabulary，通常有 32,000 到 150,000+ 个 Token），输出每个 Token 的未经归一化的对数几率值（Logits，记为 $z_t$）。随后经过带有温度（Temperature $\tau$）的 Softmax 计算概率分布：

$$P(w_t = v_i \mid w_{<t}) = \frac{\exp(z_{t, i} / \tau)}{\sum_{j \in \mathcal{V}} \exp(z_{t, j} / \tau)}$$

### 2.2 为什么纯 Prompt 会引发 JSON 格式崩溃？

当要求模型输出 JSON 时，模型是在使用统计概率模拟它在海量语料中见过的 JSON 字符串。这里存在致命的工程隐患：
* **概率波动的长尾效应**：即使某个合法闭合括号 `}` 的生成概率高达 99%，只要在几百个 Token 的生成链条中出现一次随机微小扰动，模型采样到了换行符或逗号，整个 JSON 就会直接断裂。
* **无状态语法感知**：标准的 Transformer 架构内部并没有内建“括号匹配计数器”或“状态机栈”。模型在第 200 个 Token 时，并不真正“知道”在第 15 个 Token 处打开的一个数组 `[` 是否已经闭合。
* **多余标记与废话溢出**：模型经常会在 JSON 前后添加前导说明（如 `Here is the requested JSON:`）或 Markdown 围栏代码块（````json ... ````），导致下游传统的 `json.loads()` 抛出解析异常。

## 3. 传统 JSON Mode 的局限性与幻觉漏洞

在 2023 年，OpenAI 推出了第一代 `response_format={"type": "json_object"}`（即传统 JSON Mode）。许多开发者误以为有了这个参数就能一劳永逸，但在实际生产中却遭遇了惨痛的翻车。

### 3.1 软约束的本质

传统 JSON Mode 仅仅是一种**“软提示与弱引导”**机制。模型提供商在其推理后端或前置微调中：
1. 强制要求在 System Prompt 中出现单词 "JSON"；
2. 约束模型开头的第一个有效字符必须是 `{`，末尾字符是 `}`。

### 3.2 传统 JSON Mode 的三大死穴

| 致命问题 | 现象与后果 | 生产危害 |
| :--- | :--- | :--- |
| **字段任意缺失** | 模型正确输出了合法的 JSON 语法，但声明必须存在的字段（如 `user_id`）被随机丢弃 | 下游代码触发 KeyError，导致进程崩溃 |
| **多余幻觉键（Hallucinated Keys）** | 模型自主捏造出 Schema 中根本不存在的私自扩展字段 | 破坏数据库行映射，引发未知写入风险 |
| **类型隐式漂移** | 期望数字类型 `amount: 100`，模型却输出了字符串 `"amount": "100美元"` 或包含说明 | 业务层浮点计算和数值比对彻底失效 |

因此，工业界得出明确结论：**传统的 JSON Mode 只能保证“语法符合合法 JSON”，完全无法保证“语义符合业务 Schema”**。

## 4. 约束解码（Constrained Decoding）核心原理

为了彻底根治这一顽疾，学术界与工业界（以 Outlines、Guidance、SGLang 及 OpenAI 为代表）在 2024 年全面普及了**受限解码（Constrained Decoding / Grammatical Masking）**技术。

### 4.1 Logit Masking 数学机制

约束解码不在模型训练阶段做文章，而是在**推理生成的解码采样阶段**施加数学级绝对拦截：

在每个时间步 $t$ 生成下一个 Token 前，约束解码引擎会根据当前的语法解析状态，计算出词表 $\mathcal{V}$ 中所有合法的后继 Token 集合 $\mathcal{V}_{\text{valid}} \subset \mathcal{V}$。
然后，构造一个掩码向量（Mask Vector）$M_t$：

$$M_{t, i} = \begin{cases} 0, & \text{if } v_i \in \mathcal{V}_{\text{valid}} \\ -\infty, & \text{if } v_i \notin \mathcal{V}_{\text{valid}} \end{cases}$$

将其直接叠加到模型的原始 Logits 上：

$$\tilde{z}_{t, i} = z_{t, i} + M_{t, i}$$

再送入 Softmax 计算生成概率：

$$P(w_t = v_i \mid w_{<t}) = \frac{\exp(\tilde{z}_{t, i} / \tau)}{\sum_{j \in \mathcal{V}} \exp(\tilde{z}_{t, j} / \tau)}$$

对于任何不合法的 Token（例如在需要输出闭合括号 `}` 时模型想输出字母 `a`），其掩码值为 $-\infty$，因此 $\exp(-\infty) = 0$。**不合法 Token 的采样概率被数学强制归零，绝对不可能被模型选中**！

```
                     ┌──────────────────────────┐
                     │ Transformer Model Logits │  z_t = [2.1, 0.4, 5.8, -1.2, ...]
                     └────────────┬─────────────┘
                                  │
                                  ▼
┌──────────────────────┐    ┌───────────┐
│ Grammar FSM Engine   │───►│ Logit     │  M_t = [0, -inf, 0, -inf, ...]
│ (Current State: INT) │    │ Masking   │  (Only digit tokens allowed)
└──────────────────────┘    └─────┬─────┘
                                  │
                                  ▼
                     ┌──────────────────────────┐
                     │ Masked Logits            │  z_t = [2.1, -inf, 5.8, -inf, ...]
                     └────────────┬─────────────┘
                                  │
                                  ▼
                     ┌──────────────────────────┐
                     │ Softmax & Sampling       │  Non-digit tokens have 0% probability
                     └──────────────────────────┘
```

## 5. 上下文无关文法（CFG）与下推自动机（PDA）

约束解码的核心挑战在于：**如何能够以极低的时延（微秒级），在每次采样前判定词表中数万个 Token 哪些是合法的？**

### 5.1 从 JSON Schema 到有限状态机（FSM）

JSON 数据格式在形式语言学上属于**上下文无关文法（Context-Free Grammar, CFG）**。
对于结构固定的 JSON 对象（无任意无限嵌套递归深度），可以将其编译为一个**确定性有限状态自动机（Deterministic Finite Automaton, DFA / FSM）**。

一个 FSM 由五元组构成：

$$\mathcal{M} = \langle Q, \Sigma, \delta, q_0, F \rangle$$

其中：
- $Q$：有限状态集合（例如：`WAIT_KEY`、`IN_STRING`、`WAIT_COLON`、`WAIT_VALUE`）；
- $\Sigma$：输入字符集（ASCII / Unicode 字符）；
- $\delta: Q \times \Sigma \rightarrow Q$：状态转移函数；
- $q_0$：初始状态；
- $F$：接受状态集合。

### 5.2 前缀树（Trie / Radix Index）加速查找

由于大模型的分词器（Tokenizer）产生的是 Token（可能代表单个字符、多个单词片段，如 `" age"`、`"": "`），而不是单个字符，直接在字符级 FSM 上迭代太慢。
现代约束引擎（如 Outlines、XGrammar）在模型推理初始化阶段，会将模型的全部词表预先构造成一颗**前缀树（Trie）**。
在每个生成步，系统根据当前 FSM 允许接受的字符子集，直接在 Trie 树上做快速位掩码（Bitmask）索引裁剪，仅需耗费几微秒即可产出当前步的非法 Token 掩码。

## 6. JSON Schema 标准规范全解与 Pydantic 映射

要利用大模型厂商的结构化输出能力，必须向其提供严格符合标准的 JSON Schema。

### 6.1 OpenAI Strict 模式的极端严苛约束

OpenAI 在 2024 年 8 月推出的全新 Structured Outputs 功能中，施加了极其严苛的规范约束：
1. **禁止开放式对象扩展**：所有的 Object 类型 Schema 必须显式标记 `"additionalProperties": false`，杜绝模型自由发挥添加额外键；
2. **所有属性必须标记为必填（Required）**：在 Object 的 `required` 数组中，必须包含该对象声明的**所有键**。即使字段在业务上是可选的，也必须通过联合类型声明为 `"type": ["string", "null"]`，并放入 `required` 列表中；
3. **不支持递归深度未绑定的自引用模型**；
4. **属性数量限制**：单个 Schema 顶层最多支持数百个字段，嵌套深度通常限制在 5 层以内。

### 6.2 Pydantic 自动转换为符合严格模式的 JSON Schema

在现代 Python 中，Pydantic V2 能够自动为我们处理这种繁琐转换：

```python
from pydantic import BaseModel, Field

class Address(BaseModel):
    city: str
    postal_code: str | None = Field(default=None, description="Optional postal code")

class UserProfile(BaseModel):
    user_id: int
    username: str
    addresses: list[Address]

# 生成标准的 JSON Schema 字典
strict_schema = UserProfile.model_json_schema()
# pydantic 自动处理了 required 与 nullable 映射
```

## 7. 主流云端商业大模型 Structured Outputs 实战

目前三大主流商业 API 厂商在提供结构化输出时采用了不同的技术路径。

### 7.1 OpenAI: 官方原生 client.beta.chat.completions.parse

OpenAI 原生内置了服务端受限采样（Grammar Engine），直接返回自动反序列化后的强类型对象：

```python
import os
from openai import OpenAI
from pydantic import BaseModel, Field

client = OpenAI(api_key=os.environ.get("OPENAI_API_KEY"))

class StepByStepPlan(BaseModel):
    goal: str
    steps: list[str] = Field(min_length=1)
    estimated_minutes: int

completion = client.beta.chat.completions.parse(
    model="gpt-4o-2024-08-06",
    messages=[
        {"role": "system", "content": "You are a professional project planner."},
        {"role": "user", "content": "Plan a 3-day database migration to PGVector."}
    ],
    response_format=StepByStepPlan, # 直接传入 Pydantic 类
)

# 1. 提取强类型解析结果
result: StepByStepPlan | None = completion.choices[0].message.parsed
# 2. 处理安全拒绝（Refusal）：如果模型因安全对齐拒绝回答，parsed 将为 None，而 refusal 会有值
if completion.choices[0].message.refusal:
    print("Model Refused:", completion.choices[0].message.refusal)
else:
    print(f"Goal: {result.goal}, Steps: {len(result.steps)}")
```

### 7.2 Anthropic Claude: 基于 Tool Use 的强制结构化输出

Anthropic 官方推荐的最佳实践是：**声明一个专用的单工具（Tool），并使用 tool_choice 强制模型必须且只能调用此工具**，以此获得 100% 结构化输出：

```python
import os
import anthropic
from pydantic import BaseModel

client = anthropic.Anthropic(api_key=os.environ.get("ANTHROPIC_API_KEY"))

class SentimentAnalysis(BaseModel):
    sentiment: str # "positive" | "negative" | "neutral"
    confidence_score: float
    key_evidence: list[str]

# 提取 Pydantic 的 JSON Schema 作为工具的 input_schema
tool_definition = {
    "name": "record_sentiment",
    "description": "Record structured sentiment analysis output.",
    "input_schema": SentimentAnalysis.model_json_schema()
}

response = client.messages.create(
    model="claude-3-5-sonnet-20241022",
    max_tokens=1024,
    tools=[tool_definition],
    # 强制锁定只能调用这个工具，模型无法输出任何外部自然语言废话
    tool_choice={"type": "tool", "name": "record_sentiment"},
    messages=[
        {"role": "user", "content": "The customer was thrilled with the fast delivery but noted the box was slightly torn."}
    ]
)

# 从响应的 content 块中提取工具入参并直接反序列化
for block in response.content:
    if block.type == "tool_use" and block.name == "record_sentiment":
        structured_data = SentimentAnalysis.model_validate(block.input)
        print(f"Sentiment: {structured_data.sentiment}, Score: {structured_data.confidence_score}")
```

## 8. 本地开源大模型受限采样引擎深度实战（vLLM 与 Ollama）

很多企业出于隐私与合规要求，必须将模型（如 Qwen2.5-7B, Llama-3-8B）私有化部署在内部服务器上。此时，在本地端侧启用约束解码是 Agent 运行的关键。

### 8.1 vLLM: 集成 Outlines / XGrammar 极速受限解码

vLLM（目前最流行的高吞吐开源推理框架）原生内建了强大的约束解码后端：

```python
from vllm import LLM, SamplingParams
from pydantic import BaseModel

class CodeTask(BaseModel):
    language: str
    code_snippet: str
    unit_tests_pass: bool

# 实例化本地推理引擎
llm = LLM(model="Qwen/Qwen2.5-7B-Instruct")

# 在采样参数中直接传入 guided_json
sampling_params = SamplingParams(
    temperature=0.0,
    max_tokens=512,
    guided_decoding_backend="xgrammar", # 或 "outlines"
    guided_json=CodeTask.model_json_schema() # 施加绝对文法掩码
)

prompts = ["Generate a python function to compute factorial."]
outputs = llm.generate(prompts, sampling_params)
raw_json = outputs[0].outputs[0].text

# 100% 保证可被 Pydantic 直接解析，绝对不会抛出 JSONDecodeError
task = CodeTask.model_validate_json(raw_json)
print(f"Language: {task.language}
Code:
{task.code_snippet}")
```

### 8.2 Ollama: 极简的本地 Pydantic 约束接口

Ollama 在 2024 年更新了对结构化 JSON Schema 的原生支持：

```python
import ollama
from pydantic import BaseModel

class HardwareSpec(BaseModel):
    chip_model: str
    ram_gb: int
    neural_engine_cores: int

# 直接使用官方 Python SDK 传递 format 参数
response = ollama.chat(
    model="llama3.1:8b",
    messages=[
        {"role": "user", "content": "Provide specifications for an Apple M4 Max chip."}
    ],
    format=HardwareSpec.model_json_schema(), # 核心：将 Pydantic Schema 传递给底层 Llama.cpp 引擎
    options={"temperature": 0.0}
)

spec = HardwareSpec.model_validate_json(response["message"]["content"])
print(f"Chip: {spec.chip_model}, RAM: {spec.ram_gb}GB")
```

## 9. 复杂实体与多态数据结构精准提取

简单的平铺模型容易处理，但在实际业务中，我们经常遇到**多态分支（Polymorphism）**，例如一个客服 Agent 处理的用户请求可能是“退款请求”、“发票开具”或“售前咨询”三种完全不同的数据结构之一。

### 9.1 鉴别多态（Discriminated Unions）实战

借助 Pydantic 的 `discriminator` 机制，可以让大模型自动根据类型标记，生成完全符合对应子类型的对象：

```python
from typing import Literal, Union
from pydantic import BaseModel, Field

class RefundIntent(BaseModel):
    intent_type: Literal["refund"] = "refund"
    order_id: str
    refund_amount: float
    reason: str

class InvoiceIntent(BaseModel):
    intent_type: Literal["invoice"] = "invoice"
    tax_id: str
    company_name: str
    email_target: str

class GeneralInquiryIntent(BaseModel):
    intent_type: Literal["inquiry"] = "inquiry"
    question_summary: str
    urgency_level: Literal["low", "medium", "high"]

# 鉴别多态联合类型：以 intent_type 字段作为区分依据
type CustomerIntent = RefundIntent | InvoiceIntent | GeneralInquiryIntent

class UserIntentClassification(BaseModel):
    confidence: float
    intent_payload: CustomerIntent = Field(discriminator="intent_type")

# 无论用户输入什么，输出的 intent_payload 都是精确的子类实例
raw_sample = "{"confidence": 0.98, "intent_payload": {"intent_type": "refund", "order_id": "ORD-998", "refund_amount": 128.5, "reason": "damaged"}}"
parsed_intent = UserIntentClassification.model_validate_json(raw_sample)
assert isinstance(parsed_intent.intent_payload, RefundIntent)
```

## 10. 结构化输出的生产级性能与开销剖析

天下没有免费的午餐。引入约束解码在带来绝对稳定性的同时，也对系统性能引入了新的维度考量。

### 10.1 首字延迟（TTFT: Time-To-First-Token）的增加

* **原因**：当向推理引擎（如 vLLM 或 OpenAI）提交一个新的 JSON Schema 时，引擎必须在底层将该 Schema 编译为状态机并在词表前缀树上构建索引掩码。
* **现象**：当 Schema 极其复杂（包含上百个字段或复杂的深层正则表达式）时，模型的首字延迟（TTFT）可能会显著增加 100ms ~ 500ms。
* **优化策略**：
  1. **Schema 预热与缓存**：在系统启动时预先对固定的业务 Schema 进行一次空推理，让推理服务器完成 FSM 状态机编译并缓存在内存中；
  2. **避免动态拼接 Schema**：尽量保持 Schema 结构稳定，不要根据每个请求动态修改字段名称。

### 10.2 约束解码对模型逻辑推理智商的潜在影响

学术界最新的实证研究表明：**在某些需要复杂数学推演或多步逻辑思考的任务中，如果强制模型必须“直接”从第一个字符开始输出紧凑的 JSON，模型的推理准确率会出现轻微下降**。
* **原因**：大模型需要依靠生成“思考过程（Thinking Tokens / Scratchpad）”来激发注意力机制中的上下文工作记忆。如果在第一个 Token 就强制它输出 {"answer": ...}，它失去了中间思考的缓冲区。
* **解决方案**：在 Pydantic 模型中显式设计思考字段，引导模型先思考再输出答案：

```python
class ReasonedOutput(BaseModel):
    thought_process: str = Field(description="Step by step reasoning before final conclusion")
    final_answer: int
```

## 11. 自愈与自修复管道设计（Self-Correction Pipeline）

即使有了约束解码，但在面对超长文本、网络截断或不支持服务端强受限采样的中小型开源模型时，客户端校验仍可能遭遇 `ValidationError`。生产级系统必须配备自愈（Self-Correction）管道。

### 11.1 反射纠错管道实现

当捕获到校验异常时，系统不应直接向用户报错，而是提取 Pydantic 的详细错误位置（`err.errors()`），自动组装带有错误现场的上下文，向模型发起定向纠错：

```python
import json
from openai import OpenAI
from pydantic import BaseModel, ValidationError

class UserKycRecord(BaseModel):
    user_name: str
    age: int
    national_id: str

def parse_with_self_correction(
    client: OpenAI,
    prompt: str,
    max_retries: int = 2
) -> UserKycRecord:
    messages = [
        {"role": "system", "content": "Extract KYC data in JSON format."},
        {"role": "user", "content": prompt}
    ]
    
    for attempt in range(max_retries + 1):
        response = client.chat.completions.create(
            model="gpt-4o-mini",
            messages=messages,
            response_format={"type": "json_object"}
        )
        raw_text = response.choices[0].message.content or "{}"
        
        try:
            # 尝试通过 Pydantic 严格校验
            return UserKycRecord.model_validate_json(raw_text)
        except ValidationError as e:
            if attempt == max_retries:
                raise RuntimeError(f"Failed to parse structured output after {max_retries} retries: {e}")
            
            # 提取结构化错误详情
            error_details = json.dumps(e.errors(include_url=False), indent=2)
            # 构造自我纠错消息反馈给模型
            messages.append({"role": "assistant", "content": raw_text})
            messages.append({
                "role": "user",
                "content": f"Your previous JSON output failed validation with errors:\n{error_details}\nPlease fix the issues and output the corrected JSON only."
            })

    raise RuntimeError("Unexpected pipeline loop exit")
```

## 12. 结构化输出在安全防御中的作用

结构化输出不仅是一项数据工程技术，更是**构建高安全 AI Agent 的第一道防火墙**。

### 12.1 缩小攻击面（Attack Surface Reduction）

在自然语言自由生成场景下，黑客经常通过提示词注入（Prompt Injection）诱导模型输出越狱指令、钓鱼链接或伪造的系统报错。
* **语法封锁**：当开启受限解码时，词表中除合法数据字符外的所有指令（例如 `<script>`, `sudo`, `ignore previous instructions`）在采样阶段被 Logit Masking 强制封杀。
* **字段语义隔离**：通过将不可信的用户输入严格限制在数据属性中（例如 `user_query: str`），杜绝攻击载荷逃逸进入系统的控制流指示字段（如 `is_admin_action: bool`）。

## 13. 工业级跨平台统一适配层代码全案

在实际的大型企业项目中，我们往往同时混合使用 OpenAI、Claude 以及本地部署的 Ollama/vLLM。为了让上层 Agent 业务代码与底层供应商彻底解耦，我们需要设计一个**跨平台结构化输出统一网关**。

### 13.1 抽象工厂与适配器模式全案

```python
import os
from abc import ABC, abstractmethod
from typing import TypeVar, Type, Any
from pydantic import BaseModel
from openai import OpenAI
import anthropic
import ollama

T = TypeVar("T", bound=BaseModel)

class BaseStructuredProvider(ABC):
    @abstractmethod
    def generate(self, prompt: str, schema_cls: Type[T]) -> T:
        pass

class OpenAIStructuredProvider(BaseStructuredProvider):
    def __init__(self, api_key: str | None = None):
        self.client = OpenAI(api_key=api_key or os.environ.get("OPENAI_API_KEY"))

    def generate(self, prompt: str, schema_cls: Type[T]) -> T:
        completion = self.client.beta.chat.completions.parse(
            model="gpt-4o-2024-08-06",
            messages=[{"role": "user", "content": prompt}],
            response_format=schema_cls,
        )
        parsed = completion.choices[0].message.parsed
        if parsed is None:
            raise RuntimeError(f"OpenAI refused or failed: {completion.choices[0].message.refusal}")
        return parsed

class ClaudeStructuredProvider(BaseStructuredProvider):
    def __init__(self, api_key: str | None = None):
        self.client = anthropic.Anthropic(api_key=api_key or os.environ.get("ANTHROPIC_API_KEY"))

    def generate(self, prompt: str, schema_cls: Type[T]) -> T:
        tool_name = f"extract_{schema_cls.__name__.lower()}"
        tool = {
            "name": tool_name,
            "description": f"Output data strictly matching {schema_cls.__name__}",
            "input_schema": schema_cls.model_json_schema()
        }
        res = self.client.messages.create(
            model="claude-3-5-sonnet-20241022",
            max_tokens=2048,
            tools=[tool],
            tool_choice={"type": "tool", "name": tool_name},
            messages=[{"role": "user", "content": prompt}]
        )
        for block in res.content:
            if block.type == "tool_use" and block.name == tool_name:
                return schema_cls.model_validate(block.input)
        raise RuntimeError("Claude did not return expected tool call block")

class OllamaStructuredProvider(BaseStructuredProvider):
    def __init__(self, model_name: str = "llama3.1:8b"):
        self.model_name = model_name

    def generate(self, prompt: str, schema_cls: Type[T]) -> T:
        res = ollama.chat(
            model=self.model_name,
            messages=[{"role": "user", "content": prompt}],
            format=schema_cls.model_json_schema(),
            options={"temperature": 0.0}
        )
        return schema_cls.model_validate_json(res["message"]["content"])

# 统一入口工厂
class StructuredOutputGateway:
    @staticmethod
    def create(provider_name: str) -> BaseStructuredProvider:
        match provider_name.lower():
            case "openai":
                return OpenAIStructuredProvider()
            case "claude":
                return ClaudeStructuredProvider()
            case "ollama":
                return OllamaStructuredProvider()
            case _:
                raise ValueError(f"Unsupported provider: {provider_name}")

# 使用示例
if __name__ == "__main__":
    class CityWeather(BaseModel):
        city: str
        temperature_c: float
        condition: str

    gateway = StructuredOutputGateway.create("openai")
    weather = gateway.generate("It is sunny and 26 degrees in Tokyo.", CityWeather)
    print(f"Parsed Object: {weather.city} -> {weather.temperature_c} C, {weather.condition}")
```

## 14. 生产环境避坑指南

### 坑一：字段顺序依赖陷阱（Order of Properties）
* **现象**：要求模型对复杂代码进行安全性审计并给出评级，定义模型为：
  ```python
  class SecurityReport(BaseModel):
      is_safe: bool = Field(description="Final safety decision")
      audit_logs: list[str] = Field(description="Step by step audit reasoning")
  ```
  模型给出的 `is_safe` 准确率极低，漏洞漏报率极高。
* **死因**：自回归生成是**从左向右顺序生成**的。模型必须在输出第一行就决定 `is_safe` 的布尔值，此时它尚未生成任何分析！
* **正解**：**让思考与过程字段置前，结论与判决字段置后**：
  ```python
  class SecurityReport(BaseModel):
      audit_logs: list[str] = Field(description="Step by step audit reasoning")
      vulnerabilities_found: list[str]
      is_safe: bool = Field(description="Final conclusion based on above audit logs")
  ```

### 坑二：可选字段过度惩罚 Token 消耗
* **现象**：在 Strict 模式中定义了大量可选字段 `age: int | None = None`，发现每次生成即使绝大部分是 None，模型也会老老实实逐行输出 `"age": null`。
* **死因**：OpenAI Strict 模式强制要求所有在 `properties` 中定义的键必须出现在输出 JSON 中，哪怕值是 `null`。
* **正解**：如果对象有大量稀疏的稀缺属性，切勿全部展开在顶层平铺；应将其归拢为一个通用的属性列表或使用轻量键值对结构。

## 15. 经典面试题精选与深度解析

### Q1: Logit Bias（对数几率偏置）与 Context-Free Grammar (CFG) 约束采样的底层差异是什么？为什么 Logit Bias 不能替代结构化输出？
**答题硬核要点**：
1. **静态 vs 动态**：Logit Bias 是在推理请求开始前预先配置的**全局静态偏移量**。它在整个生成过程的每一个 Step 都对指定的 Token 施加固定的加权值，无法感知当前的语法上下文；
2. **状态依赖缺失**：当生成 JSON 时，字符串内部可以包含任意字符，但在键名之后只能出现冒号 `:`。Logit Bias 根本无法做到“在第 $t$ 步只允许输出冒号，在第 $t+1$ 步只允许输出引号”；
3. **CFG 的不可替代性**：CFG 约束采样是**基于状态机的动态掩码**，在每个 Step 根据自动机当前节点动态计算合法词集，是实现结构化输出的唯一数学解。

### Q2: 为什么在生产系统对接 OpenAI Structured Outputs 时，必须同时检查 `message.refusal` 字段？
**答题硬核要点**：
1. **机制解耦**：OpenAI 官方在模型架构中将**安全拒答（Safety Refusal）**与**结构化约束解析**解耦；
2. **静默失败风险**：当用户输入的提示词触发了模型内部的内容安全红线时，模型不会强行输出符合 Schema 的 JSON，而是会生成自然语言的道歉拒答，并将此文本填入 `message.refusal` 字段，同时 `message.parsed` 将为 `None`；
3. **健壮性保障**：若代码不检查 `refusal` 字段而直接解包 `parsed`，会引发 `AttributeError: NoneType object has no attribute...` 导致接口抛出 500 异常。

```
结构化输出生产级铁律：
├── 1. 摒弃旧观念：传统 JSON Mode 只能保证语法是 JSON，无法保证字段完整性，生产必须全面升级至基于 CFG 的受限解码
├── 2. 字段拓扑优先：自回归生成从上至下，思考/分析字段置前，结论/枚举判定字段置后

└── 5. 坚守防御纵深：受限解码提供数学级语法防御，应用层配备 Pydantic 校验与自愈重试兜底，形成双层安全闭环
```
